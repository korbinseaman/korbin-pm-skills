# AI 产品经理工作流演变：深化版分享规划

## 分享目标

这场分享不做 AI 名词科普，也不把仓库目录逐项念一遍。45 分钟要回答三个更有价值的问题：

1. 为什么提示词越来越长，产品经理的交付仍然不稳定？
2. Context、Agent、Harness 分别解决哪一种系统性失败？
3. 如何把产品经理的隐性判断做成可复用、可验证、可演进的 Skill？

核心观点：AI 工作流的演进，本质上是不断把原来留在产品经理脑中、聊天记录中和临时操作中的控制信息外置。

- Prompt 外置表达意图，形成回答契约。
- Context 外置事实、约束和任务状态，形成证据契约。
- Agent 外置多步执行与工具选择，形成行动契约。
- Harness 外置权限、恢复、验证和审计，形成交付契约。

Skill 不是提示词文件。Skill 是位于 Context 与 Harness 之间的专业能力包：它决定什么时候调用、消费什么输入、怎样判断、生成什么产物，以及如何证明产物达到标准。

## 逐页内容与讲述重点

### 1. 封面：AI 产品经理的工作系统演变

- 主标题：从提示词到可验证交付
- 副标题：我的 AI 产品经理工作流、Skill 与 Harness 实践
- 开场：过去一年我最大的变化，不是换了哪个模型，而是不断把自己的判断方式、任务状态和质量标准移出聊天框。

### 2. 模型更强，交付为什么仍然不稳定

用一个任务贯穿全场：为“手机图库 AI 清理”完成研究、竞品分析、PRD 和原型。

四类常见失败：

- 事实失败：引用过期版本，把“没搜到”写成“不支持”。
- 决策失败：输出看似完整，但没有回答下一步究竟做不做、先做什么。
- 执行失败：中间产物散落在对话里，下一个步骤读不到上一步的边界。
- 交付失败：格式正确但需求漏项、原型状态不全、没有证据和验收映射。

结论：模型质量只决定局部推理上限，交付系统决定任务能否稳定完成。

### 3. 四次演进对应四种契约

| 层次 | 控制对象 | 核心契约 | 典型失败 |
|---|---|---|---|
| Prompt | 单次回答 | 回答契约 | 意图和格式不稳定 |
| Context | 事实与状态 | 证据契约 | 过期、冲突、污染、丢失 |
| Agent | 工具与动作 | 行动契约 | 选错工具、无限循环、副作用 |
| Harness | 运行环境 | 交付契约 | 无法恢复、无法验证、不可审计 |

强调：后面的层级不会替代前面的层级。Harness 仍然需要好 Prompt、好 Context 和好工具。

### 4. Prompt 工程优化的是局部回答

提示词工程真正有价值的部分：定义目标、受众、约束、输出形态和少量示例。

它无法独自解决：哪些材料可信；长任务已经完成到哪里；什么动作允许自动执行；最终产物如何验证。

关键转折：当提示词开始塞入知识库、流程、模板、检查清单和历史状态时，我们实际上已经在做 Context 和 Harness，只是还没有把它们结构化。

### 5. Context 工程不等于把文档塞满窗口

把上下文拆成四层工作集：

1. 稳定规则：角色边界、隐私与事实标准。
2. 任务契约：目标、用户、成功标准、输出要求。
3. 动态证据：按当前问题检索的材料和来源。
4. 运行状态：已完成动作、关键决定、文件位置、未解决问题。

RAG 只是动态证据进入上下文的一种机制。真正的 Context Engineering 还要决定检索预算、冲突处理、版本边界、压缩规则和哪些信息不能进入下游。

产品经理应问的不是“要不要做 RAG”，而是“这个决策最小需要哪些证据，证据不足时系统怎么表达不确定性”。

### 6. Agent 把任务建模为状态迁移

用状态机解释 Agent：

`当前状态 S(t) + 目标/约束 → 选择动作 → 工具结果 O(t) → 更新状态 S(t+1)`

PM 需要提供四类控制信息：成功条件、动作空间、停止条件、升级条件。

Agent 的价值不在于“自动多做几步”，而在于能根据观察结果改变路径。预定义 Workflow 和动态 Agent 可以组合使用。

### 7. Harness 是 Agent 的运行时产品

用“失败模式—控制机制”讲 Harness：

| 失败模式 | Harness 控制 |
|---|---|
| 长对话漂移 | 结构化文件状态、压缩与恢复点 |
| 工具产生副作用 | 沙箱、权限、审批、幂等和重试规则 |
| 搜索无限扩张 | Research Unit、检索预算和停止条件 |
| 输出看似正确 | Schema、lint、测试、渲染和人工评审 |
| 多 Skill 互相污染 | 最小输入原则、文件契约和隔离上下文 |

Harness 的产品设计对象包括：工作目录、文件协议、权限、工具描述、错误信息、日志、验证器和人工确认点。

### 8. Agent 工具的演变：从回答界面到运行环境

不要按厂商罗列，而按能力栈解释：Chat；Retrieval / Functions；MCP / Connectors；Coding Agent / Computer Use；Skills / Tracing / Evals。

工具质量决定 Agent 上限。一个工具描述必须说明用途、使用时机、输入、影响范围、是否可安全重试和常见失败。

### 9. 一个 PM 任务的端到端产物链

以“手机图库 AI 清理”为例：

`原始材料 → evidence_ledger → research_design → questionnaire → competitor_matrix → requirement_ledger → PRD → ux_contract → prototype → review_report`

每个节点都必须有明确 owner Skill、有稳定契约、保留上游证据引用，并允许从失败节点局部重跑。

### 10. Skill 包的工程结构

- `SKILL.md`：触发、排除、输入输出、决策流程和停止条件。
- `references/`：按需加载的专业方法，避免主文件成为巨型提示词。
- `templates/`：固定交付结构和平台格式。
- `scripts/`：格式、字段、统计、逻辑等确定性工作。
- `tests/evals`：防止规则、脚本和输出契约在迭代中漂移。

设计原则：判断交给模型，确定性约束交给代码；稳定信息放 Skill，任务信息放工作目录；主 Skill 只保留路由和核心决策。

### 11. 当前仓库的能力成熟度

| 能力域 | 输入输出契约 | 专业规则 | 确定性脚本 | 工作流 | 回归测试 |
|---|---|---|---|---|---|
| 用户研究 | 有 | 有 | 有 | 有 | 有，但当前存在失败 |
| 竞品矩阵 | 有 | 有 | 有 | 单 Skill 内编排 | 缺少系统化回归 |
| 新品洞察 | 有 | 有 | 有 | 无 | 局部验证 |
| 产品文案 | 有 | 有 | 有 | 无 | 局部验证 |
| PRD / 原型 | 尚未形成 | 尚未形成 | 尚未形成 | 尚未形成 | 尚未形成 |

这张表把“仓库里有文件”与“团队可以依赖的能力”区分开。

### 12. 用研 Skill 深拆：先编码决策，再生成问题

`ur-design-survey` 的核心不是生成 12 道题，而是把模糊课题变成一条可分析证据链。

1. 先确认课题、目标和四选一问卷场景。
2. 把研究目标映射为需要判断的变量和证据。
3. 再决定模块顺序、受访者分支和题量。
4. 最后才生成题干、选项和平台逻辑。

关键规则：概念必须在行为与问题测量之后出现；未用用户不能评价体验；每道题必须能说明怎样进入分析和支持产品决策。

### 13. 真实产物：12 道题背后的证据链

使用仓库中的《手机图库 AI 功能使用与需求调研》：

- Q1–Q3：分组变量，不直接证明需求。
- Q4–Q6：使用状态与最近一次任务，证明行为基础。
- Q7–Q8：亲历问题和实际后果，证明问题价值。
- Q9–Q12：需求范围、强制 Top 1、选择理由和触发场景，支持优先级决策。

逻辑门：Q4 决定使用经历题，Q9 的“目前不需要”阻断后续方案取舍，Q10 只展示 Q9 已选项。

实际 lint 结果：12 题、0 个结构风险信号、结构门禁通过。

限制：lint 只能识别格式、标记和启发式措辞风险，不能证明研究目标正确、选项穷尽或结论有效。语义质量仍需要专家评审和真实 Pilot。

### 14. Workflow 深拆：合成问卷是一台文件状态机

四个 Skill 通过文件而非聊天记忆协作：

`shared_context.md → questionnaire.md → personas.json → responses_<run_id>.xlsx → report_<run_id>`

关键隔离：画像生成不读取问卷和研究假设；每个画像在独立上下文中作答；报告只读取问卷、设计文档和选定批次 Excel；多批次必须显式选择 `run_id`。

返工传播：问卷变化只重跑模拟和报告；画像变化重跑画像之后的链路；报告失败无需重做问卷。

### 15. Harness 的真实价值：测试暴露契约漂移

当前仓库实跑结果：43 项测试，28 项通过，15 项失败。

失败集中在画像生成器：测试仍要求 `--sample-size`、`--seed`、`--group-quota` 等 CLI 契约，而当前脚本不再接受这些参数；另有 Windows 中文输出编码问题。

工程结论：`SKILL.md`、脚本、测试和示例会独立演化。没有回归测试时，文档仍然“看起来完整”，但 Workflow 已无法按原契约运行。Harness 应在交付前把契约漂移变成明确失败，并阻断下游。

现场表达应坦诚：这套能力仍处于工程化过程中，测试帮助确定下一步修复优先级。

### 16. 竞品分析 Skill：先建立证据对象

`pm-system-app-competitor-matrix` 的核心对象：

- `FeatureSchema`：从用户任务拆到 Module、Feature 和期望值类型。
- `ResearchUnit`：最小检索单元是 Competitor × Feature。
- `EvidenceRecord`：Claim、支持方向、来源等级、版本、地区、事实摘录、截图、置信度和人工确认。
- `QuantitativeEvidence`：额外记录指标定义、样本、测试条件和可比性。

分析过程：先完成证据记录，再判定 Feature 状态，再抽象产品定位，最后提出方向。不能从品牌印象直接跳到战略建议。

### 17. 一个 Feature 如何经过查询、冲突和停止条件

示例 Research Unit：`Apple Photos × 是否支持按未同步状态筛选`。这里只展示研究过程，不预设真实结论。

查询集合：官方术语、用户任务、同义机制、界面证据、反向验证和版本/地区冲突验证。

状态规则：当前版本 Tier 1 直接证明时可形成高置信判断；两个独立 Tier 2/3 一致且无反证时可以停止；“没搜到”只能得到未知；达到最大检索 Pass 或冲突仍未解决时，输出“未知 / 冲突 + 请人工确认”。

### 18. PRD 与原型 Skill 的目标架构

当前仓库没有完整 PRD / 原型 Skill，本页是下一阶段设计。

核心中间产物：`requirement_ledger.yaml`

```yaml
id: REQ-001
evidence_refs: [UR-Q7, COMP-EV-023]
problem: 用户担心 AI 清理误删原图
scenario: 存储空间不足时批量清理
requirement: 删除前显示可恢复范围与保留期限
acceptance: 支持预览、撤销和恢复状态说明
```

`pm-write-prd` 生成范围、场景、状态和验收；`pm-prototype` 生成页面、状态、跳转和文案契约；`pm-design-review` 检查每个需求是否有界面落点、异常状态和验收项。

必须覆盖的状态：空、加载、失败、权限拒绝、离线、处理中、部分成功、撤销和恢复。

### 19. Skill 开发流程：从失败样本到回归资产

1. 选择高频、边界清晰、可验收的任务。
2. 收集至少 3 个真实案例和失败样本。
3. 定义触发、排除、输入输出、确认点和停止条件。
4. 把专业判断写进 Reference，把确定性规则写进 Script。
5. 先试跑最小闭环，再增加模板和平台适配。
6. 把每次返工原因转成测试或 eval。
7. 版本化 Skill，并记录上下游契约变化。

判断是否应该做 Skill：跨任务复用且可独立验收。判断是否应该做 Workflow：需要管理多个 Skill 的依赖、状态、人工门禁和局部重跑。

### 20. 团队落地：管理能力，而不是管理提示词

建议建立团队 Skill Registry，每项能力记录：Owner、版本、适用边界、输入输出、依赖、最近 eval 状态和已知限制。

试点指标：首轮交付可接受率、证据覆盖率、关键校验通过率、人工返工时间、版本升级后的回归情况。

结尾问题：产品经理团队中，哪一个高频任务最值得先做成“有契约、有证据、有验证”的 Skill？

## 现场演示建议

如允许做 4–5 分钟现场演示，建议只展示一个链路：

1. 打开 `ur-design-survey/SKILL.md`，展示输入契约和目标—证据设计。
2. 打开真实 `questionnaire.md`，展示 Q4→Q7→Q9→Q10 的证据链和分支。
3. 运行 `lint_questionnaire.py`，说明确定性门禁与语义评审的边界。
4. 展示测试结果中的 CLI 契约漂移，说明 Harness 如何阻止假完成。

## 讲述边界

- 合成用户用于问卷 Pilot、管线验证和假设生成，不能替代真实用户，也不能估算真实市场比例。
- 当前用户研究测试存在 15 项失败，应作为工程化案例说明，不应宣称该模块已全部稳定。
- 竞品示例只演示研究单元和判定方法；没有完成真实检索时，不展示具体竞品支持状态。
- PRD 与原型页属于设计提案，必须与仓库当前已实现能力明确区分。

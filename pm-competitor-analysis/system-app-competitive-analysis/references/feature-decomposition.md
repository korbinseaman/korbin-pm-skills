# 动态 Feature 拆解规则

## 核心原则

Feature 拆解是本 Skill 的核心推理环节。不得使用通用清单机械替代课题分析。

工作链路为：

`Research Question → User Task → Module → Feature → Feature Status/Value`

正式矩阵仍采用四层结构：

`User Task → Module → Feature → Feature Status`

Research Question 是上游控制变量，不额外作为表格中的一层。

## Step 1 — 明确 Research Question

将用户给出的主题转换成一个能够影响产品决策的问题。

较好：

> 图库是否能帮助用户区分本地/云端照片、理解同步状态、组合筛选条件，并高效返回完整照片范围？

较弱：

> 对比图库筛选。

Research Question 应明确“为什么要比”和“比完要支撑什么决策”。

## Step 2 — 识别核心用户任务

优先提炼一个主用户任务。如果出现多个彼此无关的任务，说明课题过宽，应先内部归组，再构建矩阵。

## Step 3 — 生成 Module

Module 是可横向比较能力的逻辑分组，不等同于产品菜单名。

正常课题建议形成 3–8 个有意义的 Module，可选类型包括：

- 入口/可发现性；
- 能力覆盖；
- 交互/操作流程；
- 系统/云端机制；
- 反馈/状态表达；
- 安全/恢复；
- 内容/AI 生成；
- 商业化/权限限制；
- 跨设备/生态协同。

只选择当前课题真正需要的类型。

## Step 4 — 生成 Feature

一个 Feature 尽量回答一个可比较问题。

较好：
- 是否支持按同步状态筛选。
- 是否显示最近删除剩余恢复天数。
- 是否支持“存储位置 + 媒体类型”组合筛选。

过于宽泛：
- 筛选体验好不好。

通常过细：
- 每个图标、微动效或单条文案的差异，除非它本身就是研究主题。

## Step 5 — 选择 Feature 输出值类型

不得强迫所有行都使用 ✓/×。

可使用：

- `status`：真正的支持状态比较。
- `number`：数量、时延、准确率等。
- `duration`：保留期限、有效期、等待时间等。
- `price`：会员、积分、单次价格等商业约束。
- `ratio`：准确率、召回率、使用率、渗透率等。
- `text`：无法用符号准确表达的机制、条件或体验差异。

状态符号统一读取 `config/constants.yaml`。

## Feature 类型

必要时使用以下标签：

- **functional**：产品能不能做什么。
- **mechanism**：底层、端云、多设备等机制怎么运行。
- **experience**：入口、流程、反馈、可发现性、认知成本。
- **quantitative**：性能、规模、使用率、数量、价格等可测量能力。

## 颗粒度检查

冻结 `FeatureSchema` 前至少检查：

1. 该 Feature 是否直接帮助回答 Research Question？
2. 是否至少有两个竞品可以在该 Feature 上形成有意义的比较？
3. 如果把它和另一个 Feature 合并，会不会掩盖重要差异？
4. 如果继续拆细，会不会增加噪声而不是洞察？
5. 预期输出是状态、数字还是文字机制，是否清楚？

## 不同课题的动态示例

### 图库筛选

可考虑：入口、筛选维度、组合筛选、云/本地状态、结果反馈、快速清空等。

### 照片删除追溯

可考虑：删除时间、删除设备、删除来源、跨设备传播、最近删除保留、恢复、操作日志、用户可解释性等。

### AI 修图

可考虑：一键美化、生成式消除、扩图、人像、画质增强、专业控制、资源规模、速度、输出限制、收费模式等。

这些都只是拆解形态示例。正式研究必须根据具体 APP、功能和主题重新生成 FeatureSchema。

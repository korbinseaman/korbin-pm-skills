# 生成用户画像

本 Skill 为用户研究模拟构建合成人物，不描述真实个体，也不估计真实人口或产品用户分布。

## 输入

只读取 `<WORK_DIR>/用户调研/<YYYYMMDD><课题>/shared_context.md`，其中 `<WORK_DIR>` 为当前用户工作目录；格式见 [references/user_personas_input.md](references/user_personas_input.md)：

- topic：产品、服务或行为场景，只用于界定调研相关画像。
- audience_groups：产品功能可能覆盖的全量候选用户群体。
- target_audience：用户确认的本次目标群体、纳入条件和排除条件。
- sample_size：画像数量，默认 100；不得少于候选群体数量。
- 可选群体配额：用户明确给出时执行；否则均衡覆盖全部候选群体。

不得读取问卷题目、访谈提纲、研究目标、核心决策、假设或概念方案。题目对画像生成是黑盒，不能让人物提前知道研究内容。

## 核心逻辑

`personas_data/` 是跨课题复用的基础用户数据库，不是某次问卷的临时样本目录。运行前先检查全局库是否已存在：已存在时默认复用，不因新课题自动覆盖；只有用户明确要求重建时，才重新生成并使用显式覆盖参数。当前课题的 `shared_context.md` 用于定义生成范围，不把课题信息写回人物事实。

### 1. 确定画像范围与配额

先形成 generation_spec：

- 全量候选群体定义产品受众范围；目标群体用于确定构建范围，不删除其他产品受众。
- 每个候选群体至少生成一人。无用户指定配额时，群体人数差不超过 1。
- 样本量允许时覆盖当前使用者、曾经使用者和无相关经验的潜在用户。
- 所有数量和比例只表示本次合成样本构成，不得表述为真实市场比例。
- exclude 默认空。只有用户明确提出并确认排除对象时才能应用。

### 2. 构建基础画像

基础画像是不依赖本次课题、换一个研究主题仍成立的人物背景，固定分为四部分：

1. demographics：年龄、性别、宽口径居住地、婚姻状态；只有与人物设定有关时才增加其他人口信息。
2. occupation_economy：职业、专业以及模板当前定义的收入字段；没有实际内容的字段不输出。
3. general_behavior：通用搜索方式、主要信息渠道、内容偏好、屏幕时间、App 使用方式、数字工具习惯、消费偏好和 2–3 项兴趣。
4. devices：主设备及配套设备，包含品牌、型号、设备类型、系统和屏幕类别等必要信息。

基础画像要具体，但避免不必要的伪精确：收入使用区间，不生成个位数收入或高精度可支配比例；居住地使用城市层级或区域，不生成真实住址。

### 3. 构建调研相关画像

调研相关画像固定分为四部分：系统 App 使用是跨手机软件调研复用的通用维度；其余三部分由 `topic` 界定本次相关经验，但不能暴露问卷内容：

4. experience：是否有相关经验、当前/曾经/潜在使用阶段及简短说明。
5. system_app_usage：用户平时如何使用手机系统 App（如系统相册、文件、浏览器、设置、日历、电话等），包括“系统默认入口优先/第三方替代/按任务切换”等真实习惯。它是跨手机软件调研可复用的背景维度，不得提前写入本次问卷的功能答案。
6. usage_habit：有经验者的一次典型触发、实际做法和结果。
7. judgment：有经验者的成功判断标准、当前卡点和采用顾虑。

当人物没有相关经验时，不输出“相关产品或功能使用习惯”和“判断”字段，但仍输出“系统App使用习惯”，因为该字段描述日常系统 App 行为而不是本次课题的产品经验。不得用 null、空字符串或“不适用”占位；不得用相邻行为冒充产品使用经验，也不得为潜在用户预设产品判断。

不再拆分“目标、需求、困难、动机、约束”等互相重叠的抽象标签。具体行为只写一次。

### 4. 大模型生成、批量审计与落盘

本 Skill 的执行主体是大模型：它根据本文件的核心逻辑、共享上下文和 `persona_template.json` 生成具体人物，而不是让脚本从固定数组拼接“伪画像”。大模型必须先生成完整的内存对象，再写出一个临时 `personas.json`，其中包含 `generation_spec`、全量 `personas` 和合成数据限制说明。

先生成基础画像，再生成调研相关画像，最后逐人执行一致性审计：

- 学生通常为 18–29 岁，月收入应为 0–3000 元或无固定收入。
- 退休人员年龄不得低于 50 岁；60 岁以上不得无依据设为在校学生。
- 未婚人物默认无子女；家长类群体必须有子女。
- 人物年龄必须与子女阶段、职级、从业年限和收入区间相容。
- 设备品牌、型号、系统与设备类型必须相容。
- 职业、年龄、收入等背景变量不得被用于自动推断能力、态度、痛点或采用意愿。
- 不同人物至少在两项实质维度上有差异，不能只替换姓名。

审计通过后，调用 `scripts/generate_personas.py` 将大模型的 JSON 规范化并写入全局画像库；再调用 `scripts/validate_personas.py` 校验 JSON、汇总文件和每个单人 TXT。脚本只做结构化处理，不新增、改写或推断人物事实。

一致性规则用于阻止明显冲突，不用于强化刻板印象。无法可靠判断时采用宽区间或更中性的设定。

## 输出

同时参考：

- [references/io-contract.md](references/io-contract.md)：定义文件组织、批量输出约束和字段省略规则。
- [templates/persona_template.json](templates/persona_template.json)：是单个用户画像字段、顺序和表达方式的运行时来源；生成器必须实际读取该文件，不得在代码中另设一套输出字段。

模板是字段上限，不是每个画像都必须填满的固定表单。生成：

~~~text
<WORK_DIR>/用户调研/personas_data/
├── personas.json
├── persons_summary.txt
├── persons/
│   ├── P001_<姓名>.txt
│   ├── P002_<姓名>.txt
│   └── ...
└── persona_audit.json
~~~

- personas.json：供其他 Skill 读取的扁平中文键值画像，可直接作为模拟用户的角色上下文。
- persons_summary.txt：全量画像数量、按画像顺序排列且可直接解析的全量用户 ID 数组，以及群体、性别、年龄段、相关经验、使用阶段和主要判断维度的分布。该 ID 数组供 ur-user-simulator 查找画像并分发子任务。
- persons/：一人一个 TXT 文件。
- persona_audit.json：由 `validate_personas.py --output` 生成，记录结构、覆盖、条件逻辑、文件组织和人物一致性审计。

### 单人 TXT 文件

每个 TXT 文件直接按 `persona_template.json` 的字段顺序逐行输出“字段名：字段值”，不再转换成另一套“基础画像/调研相关画像/1–7 项”结构。例如：

~~~text
画像编号：P002
姓名：韩青
年龄：46
性别：男
职业：公务员
系统App使用习惯：常用系统电话和日历；需要新功能时先查看系统设置，再决定是否安装第三方 App
……
~~~

TXT 与 `personas.json` 中对应 persona 的字段、顺序和值必须完全一致。内容必须具体、简洁、不重复；不得加入标题、分组、小结、编号段落或 JSON 中不存在的人物事实。模板中没有实际内容的可选字段必须整项省略，不得为了结构完整而填 null、空字符串或“不适用”。

画像内容由当前大模型按照本 Skill 的核心逻辑生成；`generate_personas.py` 不负责创作人物事实，只负责读取大模型生成的 `personas.json`、按模板规范化字段、落盘单人 TXT/汇总文件，并配合 `validate_personas.py` 做结构审计。生产运行应将大模型的临时 JSON 传给该脚本；脚本默认不接受 `shared_context.md` 作为画像内容输入。

不得再生成合并版 personas.txt。交付时明确所有画像均为合成内容。

# VOC 分析与报告规则

## 编码原则

先判断评论是否直接涉及当前竞品和目标功能。无关的品牌讨论、单纯转发、无文本表情和明显营销内容保留在原始库，但设置 `analysis_eligible=false` 并注明排除原因。

对可分析原声编码：

- `stance`：positive、negative、neutral、mixed 或 request。
- `theme`：一个可横向比较的用户观点主题。
- `reason_tags`：用户给出的好评/差评原因。
- `scenario_tags`：触发评价的用户任务或使用场景。
- `pain_point_tags`：明确问题、故障或成本。
- `request_tags`：用户明确提出的需求。

仅将用户文字明确说出的信息归为事实；由多条原声归纳出来的内容标为分析结论。不得由互动量、样本比例或单一热门帖推断市场占比、总体满意度或功能支持事实。

## 主题结论

每个报告主题展示：有效原声数、独立原帖数、平台覆盖数、时间范围、代表原声和真实链接。使用“本次样本中”“多条原声反复提及”等限定语。跨平台、跨原帖重复出现的主题可以提高信号强度，但不能替代正式用户研究。

## HTML 报告

HTML 必须离线可打开，包含研究说明、覆盖概览、竞品对比、主题洞察、原声证据、时间/平台差异和局限。每条代表原声提供外链；如果只有原帖地址，清楚展示评论定位而不是伪造直链。

所有用户内容必须 HTML 转义。报告中只展示短摘录；完整原文位于 XLSX 原始数据工作簿。

# 输出规范

本文件定义最终产物的内容合同。Markdown 与 Word 两种格式的信息结构保持一致。

## Output 1 — 产品定位 + Feature Matrix

### 1. 结论型标题

标题必须概览整体分析结果，不能只是课题名称。

较好：

> 主流图库基础筛选已趋同，竞争重点正在转向云状态、多条件组合与筛选效率。

较弱：

> 图库筛选竞品分析。

标题生成要求：
- 一句话；
- 包含判断；
- 优先体现行业趋势、最大差异或 HarmonyOS 的关键位置；
- 适合作为汇报页标题。

### 2. 两句话关键结论

固定为两句话：

- 第一句：总结行业格局/核心竞品差异。
- 第二句：总结 HarmonyOS 所处位置及最重要机会/风险。

### 3. 产品定位区域

位于功能 Feature 之前，最多使用全局配置规定的行数。默认候选包括：

- 产品定义 / 核心定位；
- 演进思路 / 战略方向；
- 核心竞争力 / 差异化能力。

维度可以根据课题动态调整，不要求固定使用上述三项。

### 4. 功能 Feature Matrix

列为竞品，行为 Module / Feature。

优先使用全局 Feature 状态符号；如果符号不能准确表达，则直接使用简短文字或数字，例如：

- 30 天；
- 仅网页端；
- 仅云端照片；
- 会员可用；
- 最高 4K。

### 5. 竞品优势场景

在功能 Feature 区域之后增加一行“优势场景”，分别概括每个竞品在当前课题下最有代表性的优势使用场景。

不允许写“体验好”“功能强”等泛化判断，应写成具体用户任务，例如：

> 多 Apple 设备用户跨设备管理照片时链路一致、认知成本低。

如果没有可靠优势结论，可以留空。

### 6. 竞品不足

增加一行“不足”，分别概括各竞品在当前 Research Question 下最明显的短板。

没有可靠结论时可以留空；证据不足时使用“请人工确认”。

## Output 2 — 竞品机制与证据明细

建议字段：

- Feature / 机制；
- 竞品；
- 界面截图；
- 具体实现；
- 使用入口 / 交互流程；
- 关键数据 / 定量证据；
- 限制条件；
- 关键差异；
- 证据状态。

表 2 的目标不是重复表 1，而是解释“它到底是怎么做的，以及为什么与其他竞品不同”。

### UI 截图

优先使用真实竞品界面截图，截图来源规则见 `references/research-evidence.md`。

无法获得可靠截图时使用全局配置中的兜底文本，不得伪造界面。

## Output 3 — 竞品高层定位可视化

固定输出三件套：

1. 根据当前评分结果生成的一版图片；
2. 可编辑原始数据表；
3. 可基于原始数据重生成雷达图、四象限图、矩阵定位图的脚本/命令。

同时提供评分依据，确保用户可以理解和修改分数。

## Output 4 — 竞品差异与 HarmonyOS 方向

至少覆盖：

- 行业共识 / Baseline；
- 主要竞品路线差异；
- 标杆能力；
- 行业空白；
- HarmonyOS 当前位置和 Gap；
- 后续优先发力方向。

结论必须回到前面的 Feature、机制、截图和数据证据，不得脱离证据做泛化总结。

## “请人工确认”展示规则

人工确认标记必须在用户能直接看到的位置展示，不能只埋在脚注或内部记录中。

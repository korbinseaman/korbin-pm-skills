# 《从会聊天到能交付：我的 AI 产品经理工作流演变》分享规划

## 分享目标

面向产品经理团队，用 45 分钟回答三个问题：

1. 我的 AI 工作方式为什么从提示词工程，走向上下文工程与 Agent Harness。
2. Agent 工具的能力边界发生了什么变化，产品经理如何选择合适的工作方式。
3. 如何把个人经验沉淀为可复用、可组合、可验证的 Skill 与 Command，并应用到用研、竞品、PRD 和原型工作。

## 核心观点

AI 工作流演变的本质，是控制对象不断扩大：

- 对话式阶段控制“这一轮怎么回答”。
- 上下文工程阶段控制“模型基于什么材料回答”。
- Agent 阶段控制“模型如何执行任务并使用工具”。
- Harness 阶段控制“任务在什么规则、权限、文件结构和验证机制中完成”。

对产品经理而言，真正可复用的资产不是一条神奇提示词，而是包含输入契约、判断规则、工具、产物和质量门槛的 Skill，以及把多个 Skill 串成业务闭环的 Command / Workflow。

## 逐页提纲与讲述内容

### 1. 封面：从会聊天到能交付

- 副标题：我的 AI 产品经理工作流演变
- 开场问题：过去一年，我究竟是在“用 AI”，还是在“设计一套 AI 工作系统”？
- 讲述：这不是模型能力盘点，而是一条个人工作方式的演进路线。

### 2. 同一个任务，四种完成方式

- 示例任务：为“图库 AI 清理”完成需求研究、竞品判断、PRD 和原型。
- 对话式：一次生成一份看起来完整的答案。
- RAG / 上下文：把资料喂给模型，答案更贴近事实。
- Agent：模型能查资料、读写文件、运行脚本、修改产物。
- Harness：通过规则、权限、目录、验证和人工确认，稳定完成整条链路。
- 讲述重点：输出质量的问题，经常来自工作系统，而不只来自模型。

### 3. 第一阶段：提示词工程

- 核心动作：角色、任务、格式、示例、限制。
- 获得的价值：启动快，适合头脑风暴、改写、单次分析。
- 遇到的瓶颈：背景重复输入、上下文漂移、无法复现、没有证据链。
- 个人认知变化：提示词决定一轮回答的形状，但很难约束完整任务。

### 4. 第二阶段：上下文工程与 RAG

- 核心动作：建立资料库、检索、分块、元数据、引用、会话记忆。
- 对产品经理的价值：让 AI 基于公司规范、历史 PRD、用户反馈和竞品证据工作。
- 新问题：检索到资料不等于正确使用资料；材料冲突、版本边界、权限和时效仍需治理。
- 讲述重点：上下文工程控制的是模型“看见什么”和“先看什么”。

### 5. 第三阶段：Agent 模式

- Agent 的最小循环：理解目标、规划、调用工具、观察结果、修正、交付。
- 工具从“信息入口”变为“行动接口”：搜索、浏览器、代码、文件、办公应用、MCP。
- 产品经理的变化：从亲自复制粘贴每一步，转向定义任务边界并审查关键决策。
- 适用范围：跨多个文件、多步骤、有检查反馈的任务。

### 6. 第四阶段：Harness

- Harness 组成：模型、上下文、工具、工作目录、权限、规则、Skill、测试与人工确认点。
- 解决的问题：长任务失焦、错误动作、产物覆盖、质量不可验证、团队不可复用。
- 讲述重点：Harness 不是某个单一产品功能，而是让 Agent 可靠工作的运行环境和控制系统。

### 7. Agent 工具的演变

- Chat：生成文本。
- Files + Retrieval：读取外部知识。
- Function Calling / Code：执行结构化动作。
- MCP / Connectors / Computer Use：连接应用、数据和界面。
- Coding Agent / Workbench：在真实工作区持续读写、运行、验证。
- Skills / Plugins / Multi-agent：复用专业流程，按需组合能力。
- 选择原则：任务越长、动作越多、风险越高，越需要清晰的 Harness 和验证。

### 8. 我的产品经理 AI 工作流地图

- 发现：用户研究、竞品追踪、行业与新品洞察。
- 定义：机会判断、需求拆解、PRD、优先级。
- 设计：交互文案、原型、方案评审材料。
- 验证：问卷 pilot、合成用户、数据分析、规则校验。
- 沉淀：Skill、Workflow、模板、脚本、案例和测试。
- 讲述重点：每个 Skill 是原子能力，Workflow 负责端到端任务。

### 9. 当前 Skill 仓库

- 当前可识别的 9 个 Skill，覆盖用户研究、竞品分析、新品洞察和系统应用文案。
- 用户研究包含 4 个原子 Skill 和 2 个组合 Workflow。
- 竞品能力分为单功能对比、持续追踪和完整竞品矩阵。
- 新品速递 Skill 把证据账本、分析框架和演示交付串成完整任务。
- 说明：PRD 与原型生成仍是下一阶段重点，当前仓库已有产品文案能力。

### 10. Skill 与 Command / Workflow 的分工

- Skill：一个稳定、可单独调用的专业能力，定义触发条件、输入输出和质量规则。
- Command / Workflow：把多个 Skill 按业务顺序组合，并管理共享上下文、检查点和产物路径。
- 类比：Skill 像岗位能力说明书，Workflow 像一个跨岗位项目 SOP。
- 判断标准：能独立验收的能力做 Skill；有明确业务终点的多步任务做 Workflow。

### 11. 案例一：用户研究为什么拆成四个 Skill

- `ur-design-survey`：把模糊课题变成可分析问卷。
- `ur-generate-personas`：生成分层、可审计的合成画像。
- `ur-user-simulator`：隔离模拟作答并记录质量。
- `ur-synthesize-report`：清理数据，完成统计和证据化综合。
- 拆分原因：每一步输入、风险、验收方式不同；可以单用，也可以组合。
- 使用边界：合成用户用于 pilot、管线验证和提出假设，不替代真实用户研究。

### 12. 深拆 Skill：`ur-design-survey`

- 触发条件：只处理新建定量问卷，明确排除访谈、执行和已有问卷优化。
- 输入契约：课题、目标、问卷场景；场景材料不足时才提问。
- 过程：确认卡、目标—证据清单、模块蓝图、全量题目、逻辑审查、双格式交付。
- 资源分层：`SKILL.md` 管流程，references 管判断，templates 管格式，scripts 管确定性校验。
- 关键设计：在生成前先确认研究方向；在交付前运行结构与逻辑校验。

### 13. 深拆 Command：`synthetic-survey`

- 输入：研究课题与已确认问卷方向。
- 编排：问卷设计、画像生成、并行模拟、数据综合。
- 共享状态：通过 `shared_context.md` 与文件契约传递，不依赖脆弱的聊天记忆。
- 产物：问卷、画像库、个人答卷、Excel、质量报告、离线 HTML 报告。
- 人工确认点：研究方向、问卷定稿、异常样本排除和结论审阅。
- 讲述重点：Command 的价值是管理依赖和状态，而不只是连续调用四次。

### 14. 案例二：竞品矩阵从“搜集功能”变成“证据系统”

- 先定义 Research Question 和竞品选择规则，再设计 Feature Schema。
- 对每个功能状态保留 UI、机制、定量数据和来源等级。
- 对“没有找到”保持谨慎，不自动判定为“不支持”。
- 输出两层表：高层 Feature Matrix 和可追溯证据明细。
- 最后才进行评分、定位图与 HarmonyOS 方向判断。

### 15. 深拆 Skill：`pm-system-app-competitor-matrix`

- 瘦主 Skill：只保留流程合同和硬规则。
- References：竞品选择、功能拆解、证据、评分和战略判断。
- Config：统一符号、数量上限、置信度和默认目标产品。
- Scripts：并行研究计划、证据归一化和图表重生成。
- Templates：约束矩阵、明细、可视化数据和报告结构。
- 讲述重点：把高成本、易出错的部分交给脚本，把需要判断的部分留给 Agent。

### 16. PRD 与原型：下一组需要补齐的 Skill

- 当前基础：用研与竞品已经提供证据输入，文案 Skill 可覆盖命名、微文案和版本说明。
- 建议新增 `pm-write-prd`：需求证据、范围、场景、流程、状态、异常、埋点和验收标准。
- 建议新增 `pm-prototype`：读取 PRD，生成信息架构、关键流程和可点击原型，并保持需求 ID 映射。
- 建议新增 `prd-prototype-review`：检查需求覆盖、交互分支、文案、可实现性和一致性。
- 目标闭环：证据进入 PRD，PRD 驱动原型，评审问题回写 PRD。

### 17. 一个 Skill 的开发流程

- 找到高频、边界清楚、可以独立验收的任务。
- 收集真实案例，标出失败模式和必须保留的专业判断。
- 定义触发条件、输入契约、输出契约和人工确认点。
- 拆分 `SKILL.md`、references、templates、scripts 和 examples。
- 用最小任务试跑，记录失败，再补规则或确定性脚本。
- 建立结构测试、样例评估和产物校验；版本化维护。
- 经验：优先固化判断和验收，不要把所有知识堆进主提示词。

### 18. 团队采用与结尾

- 第一周：每人选择一个高频任务，记录 3 个真实案例和失败模式。
- 第二周：做成最小 Skill，明确输入输出与一个质量门槛。
- 第三周：两人交叉使用，观察是否能在不同上下文中复现。
- 第四周：把相关 Skill 组合为一个 Workflow，并建立共享仓库。
- 结束语：把 AI 从个人技巧变成团队工作系统，关键是可复用、可组合、可验证。

## 演示建议

- 第 2 页用同一任务的四种交付方式快速建立差异。
- 第 12 页现场打开 `ur-design-survey/SKILL.md`，只展示触发条件、输入契约和六步流程，不逐字阅读。
- 第 13 页展示 `synthetic-survey.md` 与产物目录，让团队看到状态和文件如何传递。
- 第 15 页展示竞品矩阵目录结构，强调脚本与专业判断的边界。
- 如果时间紧，压缩第 3–4 页；不要压缩两个案例和第 16 页。

## 资料边界

- 仓库当前包含 9 个 Skill。PRD 与原型相关的完整 Skill 尚未出现在当前目录中，因此第 16 页按“下一阶段能力设计”表达。
- 合成用户研究的使用边界需要在台上明确说明。
- Agent 与 Harness 的定义按行业实践做概念归纳，不绑定单一厂商产品。
